# House Duck Console 통합 운영 설계

**작성일:** 2026-08-03

**상태:** 사용자 승인 설계
**대상:** `houseduck.in`, Quirky Ball, 향후 Project K 및 House Duck 게임

## 1. 결론

기존 `/analytics/`와 새 어드민을 사용자 관점에서 하나의
`House Duck Console`로 합친다. 공개 진입 주소는 `/console/`이며 기존
`/analytics/`는 콘솔의 분석 화면으로 연결한다.

콘솔은 한 번의 `허용된 Google 계정 + 추가 질문 비밀번호` 인증 뒤 다음 기능을
제공한다.

- 분석: 1일·7일·28일 지표와 해당 기간 실제 플레이 기록 계정
- 플레이어: 검색·정렬·상세·운영 타임라인
- 재화·점수: 안전한 직접 조정, 이상 기록 제외, 변경 이력과 되돌리기
- 라이브 운영: 공지·우편·최소 버전·QA 계정 권한
- 구매: 향후 IAP 구매·환불·권리 상태를 위한 화면 계약
- CS: `support@houseduck.in` Gmail 문의 조회·분류·검색·답변·첨부파일
- 감사 기록: 중요한 게임 데이터 변경의 전후 값·사유·결과
- Project K: 현재는 `준비 중` 껍데기만 제공

메일 본문과 Gmail 토큰은 Supabase에 저장하지 않는다. Gmail API는 관리자
브라우저에서 직접 호출한다. 게임 데이터 읽기·수정은 서버 검증 Edge Function을
통해서만 수행한다.

## 2. 목표와 성공 조건

### 운영 목표

1. 이상 점수나 사용자를 분석 화면에서 발견한 뒤 한 번의 이동으로 상세와 수정
   화면을 연다.
2. 같은 닉네임 때문에 다른 사용자를 잘못 수정하지 않는다.
3. 재화·점수를 수정한 뒤 실행 중이거나 오래된 게임 클라이언트가 값을 다시
   덮어쓰지 못한다.
4. 지원 문의를 Gmail 웹사이트로 이동하지 않고 콘솔 안에서 처리한다.
5. 향후 결제 기능이 붙으면 새 콘솔을 다시 만들지 않고 구매 데이터 공급자만
   연결한다.

### 완료 기준

- `/console/`에서 Google 로그인과 추가 질문 인증을 모두 통과해야 데이터가 보인다.
- 인증되지 않은 요청은 분석·플레이어·수정 API에서 모두 거부된다.
- 기간별 플레이어 표는 `user_id`당 한 행이며 검색·정렬·페이지 이동이 가능하다.
- 분석 플레이어 행에서 같은 사용자의 어드민 상세 화면을 연다.
- 재화·점수 수정은 사유와 예상 버전을 필수로 받고 원자적으로 적용·감사 기록한다.
- Gmail CS에서 목록·검색·상태 변경·본문·첨부파일·답변 발송이 동작한다.
- 구매·Project K 화면은 연결되지 않은 상태를 실제 데이터처럼 보이지 않는다.

## 4. 화면 구조

### 경로

- `/console/`: 통합 콘솔
- `/console/#/analytics`: 분석
- `/console/#/players`: 전체 플레이어
- `/console/#/players/{user_id}`: 플레이어 상세
- `/console/#/operations`: 라이브 운영
- `/console/#/purchases`: 구매
- `/console/#/cs`: 고객지원
- `/console/#/audit`: 감사 기록
- `/analytics/`: `/console/#/analytics`로 연결

해시 라우팅을 사용해 GitHub Pages에서 별도 서버 라우팅 설정 없이 동작시킨다.

### 공통 셸

- 상단: 선택 프로젝트, 현재 관리자, 새로고침, 로그아웃
- 왼쪽/모바일 하단: 분석·플레이어·운영·구매·CS·감사
- 프로젝트 선택: Quirky Ball은 활성, Project K는 `준비 중`
- 모든 표: 검색, 허용된 열 정렬, 페이지 이동, 빈 상태, 오류 상태

### 분석에서 즉시 조치

기간별 플레이어 행을 누르면 플레이어 상세 패널을 연다. 선택한 기간·스토어·검색
조건은 URL에 남겨 뒤로 가도 유지한다. 상세 패널에서 다음 동작을 제공한다.

- 전체 계정 상세 열기
- 재화 조정
- 점수 기록 확인·수정·제외
- 해당 표시 코드로 CS 검색

## 5. 관리자 인증

### 인증 순서

1. Google Identity Services에서 ID 토큰을 받는다.
2. 서버가 Google 서명·issuer·audience·만료·이메일 인증을 검증한다.
3. `analytics_admins` 허용 이메일인지 확인한다.
4. 질문 `내가 처음 한 게임 이름은?`을 표시하고 답을 HTTPS로 전송한다.
5. 서버는 정규화한 입력의 해시를 Edge Secret과 상수 시간 비교한다.
6. 성공하면 Google `sub`에 묶인 30분짜리 HMAC 서명 관리자 티켓을 발급한다.
7. 이후 게임 API는 Google ID 토큰과 관리자 티켓을 모두 검증한다.

질문 정답과 평문은 저장소·HTML·JavaScript·로그·DB에 넣지 않는다. 브라우저도
정답을 저장하지 않는다. 티켓만 `sessionStorage`에 두어 같은 탭 세션에서 분석과
어드민이 인증을 공유한다.

### 방어 규칙

- 허용된 Google 계정 확인 전에는 질문 검증을 수행하지 않는다.
- 질문은 15분 동안 5회 실패하면 잠시 잠근다.
- 관리자 티켓은 Google 계정과 만료 시간에 묶는다.
- 로그아웃 시 관리자 티켓·Google 세션·Gmail 액세스 토큰을 모두 폐기한다.
- 허용 origin은 `houseduck.in`, `www.houseduck.in`, 정해진 로컬 QA 주소뿐이다.
- `service_role`, 질문 해시, 티켓 서명 키는 브라우저로 보내지 않는다.

### 서버 구성

- `supabase/functions/admin-auth`: 질문 검증과 티켓 발급
- `supabase/functions/_shared/admin_access.ts`: Google·관리자 티켓 공통 검증
- 기존 `analytics-dashboard`: 공통 관리자 티켓 검증 추가
- `supabase/functions/admin-console`: 플레이어·운영 읽기와 허용된 수정 명령

## 6. 분석 개선

### 기간별 플레이어 정의

현재 분석 이벤트는 설치 ID 기반이며 계정 ID와 의도적으로 분리되어 있다. 기존
이벤트를 닉네임이나 시간으로 억지 연결하지 않는다.

기간별 플레이어는 해당 1일·7일·28일 동안 `game_records.played_at`이 있는 계정으로
정의한다. 따라서 표 제목도 `기간 내 플레이 기록 계정`으로 명확히 표시한다. 앱을
열기만 하고 한 판도 완료하지 않은 설치는 분석 집계에는 포함되지만 계정 표에는
포함되지 않을 수 있음을 안내한다.

### 표 필드

- 닉네임 + 표시 코드
- 국가·계정 유형
- 기간 내 판수
- 기간 최고점수·최고레벨
- 최근 플레이 시각
- 현재 재화 요약
- 우편·친구·시즌 상태
- 이상 신호

### 중복 닉네임

- 행 식별과 중복 제거 기준은 항상 `user_id`다.
- 동일 `user_id`는 한 행으로 집계한다.
- 같은 닉네임의 서로 다른 계정은 합치거나 숨기지 않는다.
- 동명이인은 `닉네임 · 표시 코드`로 구분하고 `동일 닉네임` 표시를 붙인다.
- 검색은 닉네임·표시 코드·사용자 ID를 지원한다.

### 정렬과 페이지 이동

허용된 정렬 키만 서버에 전달한다. 기본 정렬은 `최근 플레이 내림차순`이며 최고점수,
판수, 닉네임, 국가, 재화로 정렬할 수 있다. 한 페이지는 50행이며 서버 페이지 이동을
사용해 전체 사용자 데이터를 브라우저에 한 번에 내려보내지 않는다.

## 7. 플레이어 상세과 타임라인

### 상세

- 프로필: 닉네임, 표시 코드, 국가, 계정 유형
- 플레이: 최고점수·레벨, 최근 게임 기록, 시즌 상태
- 경제: 젬, 스태미나, 티켓, 광고 제거, 보유권
- 운영: 미수령 우편, 친구 처리 대기, QA 권한
- 구매: 향후 연결되는 구매·환불·권리 상태
- CS: Gmail 연결 시 표시 코드로 찾은 문의
- 관리자 변경 기록

### 타임라인

게임 데이터와 관리자 감사 기록은 서버에서 시간순으로 결합한다. Gmail 데이터는
브라우저에서 직접 조회해 화면에만 합치며 Supabase 타임라인에 저장하지 않는다.
메일 본문·보낸 사람·Gmail thread ID를 서버 로그나 감사 표에 복사하지 않는다.

## 8. 재화 수정

### 수정 가능 항목

- 젬
- 스태미나 / 최대 스태미나
- 돌파 티켓
- 배속 티켓

입력은 `새 값` 방식으로 제공하며 현재 값과 차이를 같이 보여준다. 음수·정수 범위
초과·스태미나 상한 위반은 서버에서 거부한다. 수정 사유는 필수다.

### 동시 수정 안전성

현재 클라이언트의 단순 upsert는 관리자 변경 뒤 오래된 로컬 상태가 서버를 다시
덮을 수 있다. 직접 수정을 열기 전에 다음 동기화 계약을 함께 적용한다.

- 인증 사용자 전용 `save_my_account_state_v2(expected_version, state)` RPC
- 서버 행 잠금 뒤 `expected_version`이 현재와 같을 때만 버전 증가·저장
- 버전 충돌 시 클라이언트는 업로드를 멈추고 서버 상태를 다시 받음
- 관리자 수정도 같은 행 잠금과 버전 증가를 사용
- 새 앱 버전 전환 전에는 어드민 수정 버튼을 비활성화
- 전환 완료 뒤 직접 `account_states` 쓰기 권한을 회수하고 RPC만 허용

이 변경은 Quirky Ball 클라이언트의 `AccountService`에 좁게 적용한다. 다음 공개 빌드의
버전 계약이 확인되기 전에는 실사용자 재화 수정을 활성화하지 않는다.

### 감사와 되돌리기

모든 수정은 요청 ID, 관리자, 사용자, 사유, 전후 값, 상태 버전, 시각, 결과를
`admin_action_audit`에 남긴다. 되돌리기는 기존 행을 삭제하지 않고 현재 버전을 다시
검사한 뒤 반대 변경을 새 감사 행으로 남긴다.

## 9. 점수 수정

점수는 프로필 최고점수와 경쟁 게임 기록이 서로 연결되어 있으므로 한 칸만 덮어쓰지
않는다.

### 제공 동작

- 특정 게임 기록의 점수·레벨 보정
- 특정 게임 기록을 랭킹에서 제외·복구
- 프로필 최고점수·레벨 보정

### 일관성 규칙

- 점수는 0 이상이며 서버 상한을 적용한다.
- 게임 기록을 바꾸거나 제외하면 현재 시즌·국가·전체 랭킹에서 같은 규칙을 사용한다.
- 수정 대상이 현재 최고 기록이면 대체 최고점수·레벨을 명시적으로 확인한다.
- 프로필, `account_states`, 공개 랭킹 원본을 한 트랜잭션에서 맞춘다.
- 오래된 로컬 최고점수가 다시 올라오지 않도록 재화와 같은 상태 버전 충돌 계약을 쓴다.
- 경쟁 기록 원본은 삭제하지 않고 제외 상태와 사유를 남긴다.
- 주간 아카이브가 제외 상태를 보존하도록 아카이브 복사 계약도 함께 갱신한다.

## 10. 라이브 운영

1차 운영 화면은 출시 필수 항목만 제공한다.

- 공지 목록·미리보기·활성 기간
- 사용자 한 명 또는 전체 대상 보상 우편
- `min_version_code`와 레거시 `min_version`
- QA 허용 계정

위험한 변경은 현재 값, 새 값, 영향 범위, 사유를 보여준 뒤 한 번 더 확인한다.
강제 업데이트는 일반 설정과 분리하고 보안·결제·랭킹 공정성 사유가 없으면 현재 코드까지
차단하지 않는 기존 정책을 유지한다.

## 11. 구매 화면

Quirky Ball과 Project K에 실제 결제 서버 검증이 없으므로 이번에는 DB 구매 행을
가짜로 만들지 않는다. 화면과 API 응답 계약만 준비하고 `결제 미연동`을 표시한다.

향후 구매 공급자가 연결되면 다음 항목을 보여준다.

- 사용자·상품 ID·표시 상품명
- Google Play / App Store
- 구매·검증·대기·취소·환불·회수 상태
- 구매 시각·최근 검증 시각
- 테스트 구매 여부
- 연결된 entitlement와 현재 효력
- 플랫폼 주문 ID의 마스킹 표시

원본 receipt·purchase token·결제수단은 화면, DB 일반 열, 로그에 남기지 않는다.
매출은 클라이언트 분석 가격 합계가 아니라 플랫폼 검증·정산 자료를 기준으로 한다.

## 12. Gmail CS

### 권한 모델

콘솔 잠금 해제 뒤 사용자가 CS 화면을 열 때만 Google Identity Services의 token model로
`https://www.googleapis.com/auth/gmail.modify` 권한을 요청한다. 액세스 토큰은 메모리에만
두고 Gmail REST API를 브라우저에서 직접 호출한다. 만료 시 `Gmail 다시 연결` 버튼으로
새 짧은 토큰을 받는다.

제한 Gmail 데이터를 Supabase Edge Function으로 전달하거나 저장하지 않는다.

### 지원 메일 범위

- 기본 검색: `support@houseduck.in`으로 전달된 스레드
- 다른 개인 메일은 콘솔 목록에 표시하지 않음
- Gmail 사용자 라벨을 상태 저장소로 사용

상태 라벨:

- `House Duck/CS/신규`
- `House Duck/CS/답변 필요`
- `House Duck/CS/사용자 회신 대기`
- `House Duck/CS/완료`

분류 라벨:

- 결제·환불
- 계정·삭제
- 버그
- 기타

콘솔을 열었을 때 지원 주소로 온 아직 분류되지 않은 스레드를 `신규`로 표시한다.
상태는 한 스레드에 하나만 적용한다. 완료 처리 시 `완료` 라벨을 붙이고 받은편지함에서
보관하며, 다시 열 수 있다.

### 목록과 검색

- 상태·분류·읽지 않음·기간 필터
- 제목·보낸 사람·Gmail 검색 문법 검색
- 최신 메시지 시각·대기 시간·첨부 유무
- 24시간 이상 답변 필요 상태를 `주의 필요`에 표시
- 페이지 이동으로 필요한 스레드만 상세 조회

### 본문과 첨부파일

- Gmail thread 단위로 대화를 표시
- `text/plain`을 우선 사용
- HTML만 있는 메일은 DOM에 삽입하지 않고 텍스트로 변환해 표시
- 외부 이미지 자동 로드 금지
- 첨부파일은 이름·종류·크기를 보여주고 사용자가 눌렀을 때만 다운로드

### 답변

- 받는 사람·제목·답변 본문·첨부파일 확인
- `From: House Duck Support <support@houseduck.in>` 사용
- 기존 `Send mail as` 별칭이 미검증 상태라 Gmail이 요청을 거부하면 발송 성공으로
  표시하지 않고 Gmail 설정 확인을 안내
- `threadId`, `In-Reply-To`, `References`를 유지해 기존 대화에 답변
- 발송 직전 최종 확인
- 성공 시 `사용자 회신 대기`, 실패 시 기존 상태 유지
- 정해진 한국어·영어·독일어 답변 템플릿 제공
- 첨부파일은 브라우저 메모리에서 MIME으로 구성하고 서버에 올리지 않음

Gmail 자체가 메일과 상태 라벨의 정본이다. CS 행동을 별도 Supabase 티켓으로 복제하지
않는다.

## 13. 주의 필요

콘솔 첫 화면에는 다음 항목만 우선순위로 모은다.

- 비정상적으로 높은 점수 또는 반복 기록
- 재화·상태 버전 충돌
- 광고 실패 급증
- 향후 구매 검증 실패·환불·권리 회수
- 24시간 이상 답변하지 않은 CS
- 강제 업데이트·공지 설정 오류

자동 제재는 하지 않는다. 오너가 원본과 타임라인을 보고 명시적으로 조치한다.

## 14. 서버 데이터와 권한

### 새 서버 데이터

- `admin_action_audit`: 게임 데이터 관리자 변경 이력
- `admin_auth_attempts`: 질문 실패 횟수와 잠금 시간
- 점수 기록의 관리자 제외·보정 메타데이터
- 계정 상태 낙관적 잠금 RPC

모든 새 공개 스키마 테이블은 RLS를 켜고 `anon`, `authenticated` 직접 접근을 회수한다.
관리자 변경 함수가 `SECURITY DEFINER`를 써야 할 때는 `search_path = ''`, 명시적 객체명,
`PUBLIC`/`anon`/`authenticated` 실행권한 회수, `service_role`만 허용을 같이 적용한다.

### 브라우저에 내려주지 않는 값

- service role·Edge Secret·질문 답·티켓 서명 키
- 복구 코드·refresh token
- Gmail access token의 영구 저장본
- Gmail 메일 원문 복제본
- 결제 receipt·purchase token

## 15. 오류 처리

- Google ID 만료: 첫 로그인으로 복귀
- 관리자 티켓 만료: 질문만 다시 요청
- Gmail 토큰 만료: 게임 콘솔 세션은 유지하고 Gmail만 다시 연결
- Gmail 발송 실패: 초안 본문을 메모리에 유지하고 재연결 안내
- 상태 버전 충돌: 수정·업로드 중단, 최신 서버 값을 다시 표시
- 관리자 변경 실패: 감사 행에 실패 원인 코드만 기록하고 값은 변경하지 않음
- 구매 미연동: 빈 표 대신 `아직 결제 시스템이 연결되지 않았습니다` 표시
- Project K: 활성 기능처럼 보이지 않는 `준비 중` 화면

오류 메시지와 로그에는 토큰, 질문 답, 메일 본문, receipt를 포함하지 않는다.

## 16. 검증

### 정적·단위 검사

- 관리자 티켓 서명·만료·계정 불일치
- 질문 입력 정규화·실패 제한
- 검색·정렬 허용 목록·페이지 경계
- `user_id` 중복 제거와 동명이인 보존
- 기간별 플레이어 집계
- 상태 버전 일치·충돌·재조회
- 재화 범위와 점수 제외·복구
- 감사 이력과 되돌리기
- Gmail MIME 생성·본문 안전 변환·상태 라벨 전환
- Pulse 모델 기존 회귀

### 권한 검사

- anon·일반 authenticated·다른 Google 계정 거부
- 허용 Google 계정도 질문 전에는 거부
- service role과 Secret의 공개 파일 부재
- 새 테이블 RLS/GRANT와 함수 실행권한
- Gmail 토큰·메일·결제 토큰의 서버 요청·로그 부재

### 브라우저 QA

- 데스크톱 Chrome 계열과 390px 모바일 뷰
- 키보드 탐색·포커스·표 스크롤·다이얼로그
- 로그인 → 질문 → 분석 → 플레이어 → 수정 미리보기
- CS 연결 → 검색 → 스레드 → 라벨 변경 → 답변 미리보기
- 실제 Gmail 발송은 오너가 받을 테스트 주소와 명시적으로 승인한 뒤 한 번 수행

시스템 브라우저 검증은 실제 Android/iOS 기기 증거로 보고하지 않는다.

## 17. 배포 순서

1. DB migration과 Edge Function을 staging/로컬 계약으로 검증한다.
2. Gmail API와 OAuth origin·테스트 사용자를 준비한다.
3. 통합 콘솔 UI를 배포하되 위험한 수정은 비활성화한다.
4. Quirky Ball `AccountService`의 상태 버전 충돌 계약을 적용·자동 QA한다.
5. 새 클라이언트 코드가 배포 준비되면 관리자 수정 기능을 활성화한다.
6. 분석·플레이어·CS 읽기 기능을 검증한다.
7. 승인된 테스트 계정으로 재화·점수 변경과 복구를 검증한다.
8. 전체 사이트 검사와 live cache-busting 확인을 수행한다.

기존 분석 함수가 새 인증을 요구하기 전에 새 콘솔·인증 함수를 먼저 배포해 분석 접근이
중간에 끊기지 않게 한다.

## 18. 오너가 필요할 수 있는 작업

에이전트가 가능한 설정·코드·배포는 직접 처리한다. 다음 단계만 Google 보안 정책상
오너 입력이 필요할 수 있다.

1. Google Cloud 또는 Supabase가 재로그인을 요구할 때 로그인·2단계 인증 승인
2. Gmail 제한 권한 동의 화면에서 관리자 계정으로 승인
3. `support@houseduck.in` Send mail as 별칭이 실제 `accepted`인지 확인
4. 실제 메일 발송 QA 전에 받을 주소와 발송 승인

Google OAuth 앱을 External Testing으로 유지하면 제한 권한 재동의가 주기적으로 필요할
수 있다. 이 경우에도 Gmail 비밀번호나 장기 토큰을 서버에 저장하는 방식으로 우회하지
않는다.

질문 정답, Gmail 비밀번호, App Password, refresh token을 채팅이나 소스에 다시 입력할
필요는 없다.

## 19. 구현 원칙

- 기존 Pulse 모델·Google ID 검증·Supabase 운영 뷰를 재사용한다.
- 새 프레임워크나 빌드 도구를 추가하지 않고 현재 정적 HTML/CSS/JavaScript 구조를
  유지한다.
- Gmail은 Google의 브라우저 토큰 모델과 REST API를 직접 사용한다.
- 위험한 수정은 서버 한 지점에서 검증·트랜잭션·감사한다.
- 기능이 없는 구매·Project K 화면은 데이터를 꾸며내지 않는다.
- 출시 전 핵심 운영에 필요하지 않은 역할 관리·대량 작업·CRM 자동화는 만들지 않는다.
