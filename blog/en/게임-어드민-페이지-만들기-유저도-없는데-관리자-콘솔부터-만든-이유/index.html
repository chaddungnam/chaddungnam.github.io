Making a Game Admin Page | Why I Built the Manager Console First Even Without Users

August 10, 2026
KoreanEnglishDeutsch日本語
Automatic translationThis page was automatically translated from Korean and may contain unnatural wording. Read the Korean original

I didn't build the game manager console

because I hated touching Supabase directly.

 

When vibe coding, some people love the terminal,

and some people love desktop programs and GUIs.

 

I am definitely the latter.

 

For server operations too, rather than opening logs and tables one by one,

I wanted to see the necessary information on a processed screen.

 

If possible, without even opening my laptop,

I wanted to check status on my phone and finish necessary operations.

 

 

There aren't even any users yet, but I made the admin page first.

Quirky Ball is still before its official release.

 

Yet the House Duck Console already has

analytics, players, operations, purchases and refunds, customer support, and audit log menus.

 

The order might seem a bit strange.

 

However, after launching the game and running into problems,

I thought making operational tools only at that point would be too late.

 

How long users played the game,

where they dropped off,

whether they returned the next day,

and whether ads were playing too frequently

were things I didn't want to ponder for the first time only after launch.

 

Having already worked in the industry

and witnessed countless trial and errors,

this was the conclusion I reached.

 

Since there is already an AI that can handle everything

as long as the requirements are clear, what is the problem?

 

 

Instead of the terminal, I wanted to make judgments from a single screen.

Supabase stores game data

and serves as the foundation connecting authentication and server features.

 

However, database tables

are not screens where operators can immediately get answers.

 

Looking up play time, completion rate, revisit rate, ad view rate,

and gem and stamina usage separately

is different from seeing "What is strange about this game right now?" at a glance.

 

So rather than ending with laying out raw data

in a readable way,

I tried to turn it into questions I would actually make decisions on.

 

If I need more players to accumulate before making a judgment,

I display it as is without fabricating a plausible conclusion.

 

 

What I needed wasn't a pretty graph

but a screen telling me what to fix first in the next update.

 

 

I wanted to spot unusual users in analytics and handle them right away.

After checking insights,

I didn't want to open Supabase or other tools again.

 

Search nicknames and display codes in the player list,

and check game count, high score, currency, and recent play.

 

Exclude or adjust abnormal scores from rankings,

issue or retrieve items if necessary,

and make it possible to send reward mail to specific users.

 

On the operation screen,

you can change the minimum supported version and notices,

and also send a general reward mail.

 

By viewing purchase and refund records,

I also added a flow to handle inquiries

arriving at support@houseduck.in within the same console.

 

The user sanctions I'm talking about

are not automatic sanctions that block people with a single button.

 

It is closer to a method where you check actual records

and select only the necessary measures,

such as excluding scores or retrieving items.

 

Important changes require entering a reason and confirming once more,

and audit logs record who changed what.

 

 

I didn't want to operate only when sitting in front of my laptop.

A 1 developer is a developer, a QA,

a planner, and a customer service representative all at once.

 

You cannot always sit in front of a desk.

 

When error reports come in from outside,

or when metrics look abnormal right after an update,

I wanted to check status on my phone and execute limited operation functions.

 

Of course, that doesn't mean opening all dangerous features on mobile.

 

Making lookups fast,

changes limited to necessities,

and irreversible tasks go through confirmation and logging is the goal.

 

The reason I liked GUIs is also here.

Even on a small screen, it was easy to distinguish what I was currently looking at

and which buttons modify actual data.

 

 

Security was handled reliably.

The console is not a service exposed to the outside.

 

First, log in with an authorized Google account,

and then it opens only after answering once more to a question that only I can immediately recall.

 

 

"What is the name of the first game I played?"

 

It is not a device created to look like incredible security technology.

 

Actual permissions are rechecked on the server,

and this question is closer to a door that once more blocks entry from another account or an open browser by mistake.

 

As features were rapidly expanded through vibe coding,

I felt that these small boundaries became even more important.

 

 

Because it was vibe coding, a GUI was needed even more.

AI makes code quickly.

 

However, if I have to remember table names and commands every time,

and re-explain which values are needed for which task,

I have to return to development mode every time I operate it.

 

The admin screen fixes that process into buttons and forms.

 

It checks in the order I intended,

accepts only designated inputs,

and asks once more for dangerous tasks.

 

Rather than to eliminate the terminal,

it is like productizing repetitive operations into a GUI.

 

 

It is not yet a completed admin.

Just because a feature was built did not mean it could be operated right away.

 

Sometimes buttons failed because server functions were missing,

and there were times when permission settings did not match actual operation data, so it had to be fixed again.

 

Project K menu is still close to a shell,

and areas that could not be automatically connected, such as store refund notifications, still remain.

 

Many cards lack data because it is before the official launch.

 

Still, if you build them from now on,

you can avoid panicking about what to check after the first user comes in.

 

House Duck Console is not a flashy-looking dashboard.

 

To view the state of the game at a glance,

and to carefully handle only necessary tasks anytime and anywhere,

it is closer to my own operational desktop program.
