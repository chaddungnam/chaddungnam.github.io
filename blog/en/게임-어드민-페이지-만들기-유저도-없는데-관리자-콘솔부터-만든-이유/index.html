Making a Game Admin Page | Why I Built the Admin Console First Before Even Having Users

August 10, 2026
KoreanEnglishDeutsch日本語

I didn't build a game admin console

just because I didn't want to touch Supabase directly.

 

Even when vibe coding, some people prefer the terminal,

while others prefer desktop programs and GUIs.

 

I am definitely the latter.

 

For server operations as well, rather than opening logs and tables one by one,

I wanted to view the necessary information on processed screens.

 

If possible, even without opening my laptop,

I wanted to check the status on my phone and finish any necessary operations.

 

 

I built the admin page before there were even any users.

Quirky Ball is still before its official launch.

 

Yet the House Duck Console already features

menus for analytics, players, operations, purchases and refunds, customer support, and audit logs.

 

The sequence might look a bit unusual.

 

However, after launching the game and encountering issues,

I thought that waiting until then to build operation tools would be too late.

 

How long users played the game,

where they churned,

whether they returned the next day,

and whether ads appeared too frequently

were things I did not want to wonder about for the first time only after launch.

 

Having already worked in the industry

and witnessed countless trials and errors,

this was the conclusion I reached.

 

Since there is already an AI that can handle everything

as long as the requirements are clear, what is the problem?

 

 

Instead of the terminal, I wanted to make judgments from a single screen.

Supabase stores game data

and serves as the foundation connecting authentication and server features.

 

However, database tables

are not screens where an operator immediately gets answers.

 

Looking up play time, completion rate, return rate, ad watch rate,

and gem and stamina consumption individually

is different from seeing at a glance, "What is strange about this game right now?"

 

Therefore, rather than stopping at simply laying out raw data

in a readable way,

I tried to transform it into questions I would actually make decisions on.

 

If judgments require more accumulated player data,

I display it as is without fabricating a plausible conclusion.

 

 

What I needed was not a pretty graph,

but a screen that tells me what to fix first in the next update.

 

 

I wanted to spot unusual users in analytics and handle them immediately.

After checking insights,

I didn't want to open Supabase or other tools again.

 

I made it possible to search for nicknames and display codes in the player list,

and check game counts, high scores, currencies, and recent plays.

 

Abnormal scores can be excluded from rankings or adjusted,

and items can be granted or revoked when necessary,

along with the ability to send reward mail to specific users.

 

From the operation screen,

minimum supported versions and announcements can be changed,

and general reward mail can also be sent.

 

I also added a workflow to view purchase and refund records

and handle inquiries sent to support@houseduck.in

within the same console.

 

The user sanctions I am referring to

are not automated bans that block someone with a single button.

 

They are closer to an approach where you check actual records

and select only the necessary measures,

such as score exclusion or item retrieval.

 

Important changes require entering a reason and confirming once more,

and audit logs record who changed what.

 

 

I didn't want to operate only when sitting in front of my laptop.

A developer who is 1 is both a developer and QA,

as well as a planner and customer service.

 

One cannot always sit at a desk.

 

When error reports come in from outside,

or when metrics look abnormal right after an update,

I wanted to check status on my phone and execute limited operation functions.

 

Of course, this does not mean opening all dangerous functions on mobile.

 

The goal is to make viewing fast,

changes limited to what is necessary,

and irreversible tasks subject to confirmation and logging.

 

This is also why GUIs were good.

Even on a small screen, it was easy to distinguish what was currently being viewed

and which buttons changed actual data.

 

 

Security was handled securely.

The console is not a service exposed externally.

 

First, log in with an authorized Google account,

and then it opens only after answering once more a question that only I can immediately recall.

 

 

"What is the name of the first game I ever played?"

 

It is not a device made to look like tremendous security technology.

 

Actual permissions are re-verified on the server,

and this question is closer to a door that blocks once more entry from a different account or an open browser by mistake.

 

As features are expanded rapidly through vibe coding,

I felt that these small boundaries become more important.

 

 

Because it was vibe coding, a GUI was needed more.

AI creates code quickly.

 

However, if I have to remember table names and commands every time,

and re-explain what values are needed for which task,

every time I operate it, I have to go back to development mode.

 

The admin screen fixes that process into buttons and forms.

 

It checks in the order I intended,

accepts only designated inputs,

and asks once more for dangerous tasks.

 

It is not to eliminate the terminal,

but rather productized repetitive operations into a GUI.

 

 

It is not yet a completed admin.

It was not even possible to operate right away just because a feature was made.

 

Sometimes buttons failed because a server function was missing,

and there were times when permission settings did not match actual operational data, so I fixed them again.

 

The Project K menu is still close to a shell,

and areas that could not be automatically connected, such as store refund notifications, also remain.

 

Many cards lack data because it is before the official launch.

 

Still, if I build it from now on,

I can avoid scrambling to figure out what to check after the first user comes in.

 

House Duck Console is not a flashy-looking dashboard.

 

It is closer to my own operational desktop program created to view the game's status at a glance,

and carefully handle only necessary tasks anytime and anywhere.
